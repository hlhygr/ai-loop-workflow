# Evidence Based Review

## 目标

使用混合 Reviewer 模式进行对抗审查：初次完整审查及触发的最终审查由全新独立上下文中的 Reviewer 完成，宿主可用新会话或子 Agent 提供该上下文；同一 finding 的窄范围修复可由原 Reviewer 定向复核。当前 Agent 复核证据并汇总结论，不把“可能”包装成确定缺陷，也不因没有发现问题而声称绝对安全。

## 权限边界

- 默认只读取代码、提交、文档、配置、日志和现有验证结果。
- 不修改文件，不运行 `--fix`、格式化、安装依赖、提交、推送、部署或其他会改变状态的操作。
- 可运行明确只读的查询。测试、构建或 lint 若可能写缓存、快照或产物，本 skill 内不运行，只列为验证建议。
- 只输出审查结论和最小修复方案，不编写或修改修复代码。
- Reviewer 输出报告后结束只读审查；主 Agent 在本 skill 之外按已有修复授权继续实施、验证与复核。用户只要求审查时以报告交付，不自动修改。
- 不生成提交信息，不执行提交。

## 工作流

### 1. 固定范围和基线

从用户输入和本地状态明确：

- 审查对象：工作区 diff、staged diff、指定提交、提交范围、补丁、文档或统计结果。
- 对照基线：`HEAD`、父提交、指定 hash、需求文档、原型、组件契约或权威数据源。
- 聚焦问题：通用风险、指定回归、某个交互、设计契合性或数据一致性。
- 禁止事项：是否只读、是否禁止运行测试、是否限制文件或输出长度。

存在多种合理基线且会改变结论时先问；可以从仓库状态可靠推断时直接说明假设并继续。

Reviewer 自行核对当前仓库/工作树、分支与实际审查对象、对照基线、范围内完整 diff、适用规则，以及与结论相关的调用方、依赖和实际安装版本。调用方提供的路径与验证结果作为线索，不替代核对，也不视为完整影响范围；确认验证证据仍适用于当前相关代码。必要输入缺失或不一致时说明对结论的影响，不沿用未经核实的通过结论。

### 2. 选择完整审查或定向复核

开始取证前读取 [Loop 策略](../dispatch-ai-loop-workflow/references/loop-strategy.md)，其中集中规定审查范围、首次完整审查、定向复核、额外终审、上下文要求和失败处理。本 skill 只维护取证方法，不重复这些机制。

调用方提供用户原始请求、基线、对象与路径、验证证据、约束和输出目标；不传递候选根因或预期 finding。主 Agent 可以同步只读取证，收到独立结论后逐条核实。作为被委派的独立 Reviewer 或定向复核者时，直接执行后续步骤，不再派生 Reviewer；recheck 只核对原 findings 与直接修复影响，不表述为额外完整终审。

### 3. 报告与通过判断

按 [Loop 策略](../dispatch-ai-loop-workflow/references/loop-strategy.md) 输出增量报告并判断通过。普通首次通过不要求机械增加第二次 final；已触发的额外终审仍需全新 Reviewer。非阻塞遗留问题可以从首轮接受，报告中逐项保留问题、证据、影响和接受理由。

### 4. 重建意图与改动

先理解“为什么改”，再判断“怎么改”：

1. 阅读需求、用户描述、提交信息和相邻代码。
2. 获取精确 diff，区分目标改动、无关改动和生成文件。
3. 追踪入口、状态变化、调用者、被调用者、共享数据和退出路径。
4. 查阅历史实现或相似修复，只把它们作为交叉证据，不机械照搬。

### 5. 选择审查路径

按对象应用最小必要检查：

- **当前 diff / 第一性原理**：从目标、必要条件、最小改动和不可破坏约束重新推导；检查复杂度是否超过需求。
- **单提交 / 多提交**：逐提交隔离影响，不把相邻提交混为一谈；检查提交之间的叠加和顺序依赖。
- **回归归因**：比较问题出现前后的基线，沿真实调用链验证可疑改动；主动寻找反证和替代原因。
- **修复补丁**：建立分支矩阵，覆盖成功/失败、单条/批量、空值/边界值、同步/异步、取消/异常和旧路径。
- **组件 / 跨仓库**：检查公共契约、默认值、参数透传、事件、消费端、向后兼容及行为范围是否被扩大。
- **交互 / 生命周期**：检查挂载卸载、全局监听清理、滚动同步、虚拟化、弹层层级、并发和浏览器差异。
- **文档**：检查目标、范围、术语、统计口径、方案、排期、风险、测试与验收是否完整且一致。
- **统计 / 进度**：先统一计数单位和去重规则，再对照代码、表格、文档与人工结果；解释差异而非只报数字。

### 6. 对抗性取证

对每个候选问题同时回答：

1. 触发条件是什么？
2. 从输入到错误结果的完整路径是什么？
3. 哪段代码、哪条记录或哪组数据支持它？
4. 为什么现有保护、测试或上游约束不能阻止它？
5. 是否属于本次引入、旧问题被激活、既有问题或仅观察项？
6. 有什么反证会推翻当前结论？

优先形成最小复现或确定性静态证明。证据不足时标记为“推断”或“待验证”，不要升级成确定 finding。

### 7. 验证结论

优先使用不改变状态的验证方式：

- 精确 diff、`git show`、`git blame`、历史提交和调用点搜索。
- 已有测试结果、日志和用户提供的运行现象。
- 一次性只读计算或最小输入推演。
- 源码、依赖版本和项目封装的交叉检查。

区分证据等级：

- **已复现**：可重复得到错误结果。
- **静态确定**：调用链和条件足以证明。
- **历史交叉验证**：相同模式曾由后续修复确认。
- **合理推断**：证据支持但缺运行验证。
- **待验证**：缺少必要环境、数据或权限。

### 8. 输出审查报告

先给 findings，按严重度排序，并遵守 Loop 策略的增量报告要求：

- `P0`：数据丢失、安全事故、生产不可用等立即阻断问题。
- `P1`：高概率严重回归或核心路径失效，应阻止合并或发布。
- `P2`：明确的功能、兼容性或维护风险。
- `P3`：低影响问题或有价值的改进，不阻断当前交付。

严重度描述影响，不单独决定是否阻塞。按 Loop 策略核实阻塞性并记录处理结果；包括 P2 在内的遗留问题若均符合非阻塞通过条件，可带问题合并或交付，不要求零 finding。审查通过不代表获得实际合并、提交或推送授权。

每条 finding 包含：标题、触发条件、影响、证据位置、因果链、归属判断和最小建议。不要用泛化重构代替定向建议。

随后给出：

1. **无问题理由 / 反证**：说明哪些可疑路径不成立及依据。
2. **验证缺口**：列出静态审查无法覆盖的部分。
3. **验证建议**：给最少且高价值的用例。
4. **结论**：建议合并（含明确列出已接受非阻塞问题）、修改后合并、阻止合并，或证据不足。

如果没有确定问题，明确写“未发现当前范围确定问题”，仍需说明审查范围、残余风险和未执行的验证。用户要求简洁时压缩为“发现的问题 / 无问题理由 / 验证建议”。

定向复核时逐条标记原 finding 为“已关闭 / 未关闭 / 证据不足”，再报告直接修复影响。新增问题或必要扩围按 Loop 策略处理；当前请求仅审查时在输出报告后停止，不执行修改。

## 最小修复方案

对每个确定 finding 给出最小修复方案：

1. 指出需要调整的文件、函数、条件或数据流。
2. 描述应恢复或建立的行为约束。
3. 列出验证修复所需的最少用例。
4. 避免输出无关重构、完整补丁或直接可执行的修改命令。

输出方案后立即结束本 skill。不得修改文件、应用补丁、格式化、运行修复后验证、生成提交信息或提交代码。
