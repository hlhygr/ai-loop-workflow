# 按需经验候选

仅用户要求复盘、沉淀或准备候选时使用；不属于核心交付流程，不默认建候选或登记状态。简单建议直接给来源、拟改内容和验证方法即可；需要独立留档或多候选跟踪时才使用下方模板和状态。任何实际修改仍按适用 AGENTS 和用户授权执行。

## 触发条件

- 用户明确要求复盘、沉淀、生成经验候选或从近期对话创建 skill。
- 在已授权的复盘范围中，筛选可重复流程、反复纠正的边界或稳定验证方式。

不要仅因任务完成就自动创建经验候选。一次性事实、纯业务判断和已有规则覆盖的偏好不进入候选。

## 来源

优先读取当前 plan 的 `task_plan.md`、`findings.md` 和 `progress.md`，依据本轮已完成阶段和交付记录提取证据。历史 `delivery.md` 可作为当时的来源材料，不要求整个持续计划已经完成。需要跨任务证据时，发现适用的用户技能或读取用户授权的来源；不自行扫描会话历史，不只凭当前线程概括“高频”。

## 候选分类

| 目标层 | 适用内容 | 不适用内容 |
|---|---|---|
| AGENTS | 跨任务稳定原则、授权和工作区边界 | 领域详细步骤 |
| 现有 skill | 已有能力的稳定纠正、输入/输出或验证改进 | 与触发范围无关的扩张 |
| 新 skill | 高频、边界清晰、输入输出和验证稳定的独立流程 | 一次性任务或一句命令 |
| 长期知识 | 需要检索的领域事实、架构与决策依据 | 活跃任务状态 |
| 自动化候选 | 确定性高、默认只读、失败影响低的重复检查 | commit、push、部署、发送消息或生产写入 |

## 生成候选

用户需要独立留档候选时可运行：

```bash
python3 skills/dispatch-ai-loop-workflow/scripts/init-learning-candidate.py --plan-dir <计划绝对路径> --name <候选名>
```

`--plan-dir` 必须显式给出，不解析宿主默认计划。脚本从该计划的 `progress.md`（或 `--source` 显式指定的计划内来源）创建 `learning_candidate-<名称>.md`；省略 `--name` 时使用含微秒的时间戳。每轮可创建新候选，同名仍拒绝覆盖，不依赖 delivery 状态。旧 `learning_candidate.md` 保留；恢复既有候选时继续编辑原文件，不重复生成。随后填入：

1. 至少两条可定位证据；单次高影响纠正可作为例外，但要说明原因。
2. 候选目标层、适用范围和明确不做。
3. 与现有 AGENTS、skills、知识和自动化的重复/冲突检查。
4. 建议变更与验证方式，不直接实施。

## 人工闸门

- `proposed`：只允许完善候选。
- 用户明确批准目标层、范围和动作后才可标记 `approved` 并进入对应实施流程。
- 用户拒绝或证据不足时标记 `rejected`，不修改任何目标层。
- 实施完成并验证后才标记 `applied`，同时在来源计划的 `progress.md` 中记录回流结果。

批准一个候选不授权相邻候选，也不授权 commit、push、用户知识库写入、消息、发布或部署。
