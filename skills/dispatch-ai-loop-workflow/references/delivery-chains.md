# 领域检查清单

只读取当前领域对应的一节。通用实施、验证与授权遵循适用 AGENTS；独立审查触发见 [任务路由](task-routing.md)，收敛规则见 [Loop 策略](loop-strategy.md)。本文件不要求额外规划、固定动作游标或逐步登记。

## 组件交付链

- 核对组件源码、配置适配层、真实调用方、实际安装包与版本；明确契约、默认行为及兼容要求。
- 各组件库、demo/docs 和授权消费仓库分别检查规则、未提交改动和验证能力；不假设消费端结构一致，不把组件库通过当作消费端已升级。
- 实现、消费端适配、表达公共契约的 demo 与文档尽量在完整审查前准备好，一起验证契约一致性。根据仓库约定和实际发现的用户领域技能维护文档，并执行适用的结构、diff、构建检查。
- 审查后的纯文字收尾按需验证即可；若文档暴露实现或契约问题，按 Loop 策略回到修复与必要复核。
- 交付可定位的契约变化、逐仓库验证、未覆盖消费端与版本/发布状态。恢复只维护计划中的唯一下一步，不使用 `chain/status/next_action/last_completed` 固定游标。

只改组件 README 时直接处理或使用匹配的用户技能，不启动完整链。

## 复杂排障链

- 固定现象、触发条件、环境与基线，优先获得最小复现；沿真实输入、状态和调用链取证。
- 多假设时保留支持证据、反证、替代解释和重要失败尝试，避免对没有新证据的补丁反复叠加。
- 验证先针对复现和直接影响，再按风险补相邻回归。区分已复现、静态确定、合理推断与环境缺失；只诊断时不实施修复。

## 日常开发链

- 页面首次开发根据需求与原型，正式接口到达后从现有实现继续联调；按 [任务路由](task-routing.md) 发现实际可用的用户技能。未知接口保留明确待对接标记，不虚构 API 或响应结构。
- 验证应能覆盖本次行为、交互与数据流；静态检查、构建、浏览器与真实接口的结论分别说明。

## 测试执行链

仅用于依据既有用例在指定环境执行并报告；编写用例不进入本链，发现失败不自动授权修复。

- 固定用例来源、筛选条件、目标环境、前置数据、预期及允许的状态变化。执行指定用例的授权仅覆盖指定环境内必要步骤，不扩展到无关清理、云表格写回或代码修改；生产、删除等动作仍核对对应授权。
- 按依赖和数据污染风险安排用例；有明确契约顺序时遵循契约。写操作前记录基线与可识别数据，操作后确认结果。超时先读状态，不盲目重放可能已完成的写操作。
- 每条记录预期、实际、可观察证据及外部状态。`PASS` 为实测符合预期；`FAIL` 为实测不符；`BLOCKED` 为缺权限、数据或环境条件；`NOT_RUN` 为范围、风险或前序依赖导致未执行。点击完成、接口成功或无报错不能单独证明通过。
- 结束时核对创建、修改、删除、保留和未能清理的对象；清理也需授权，不用恢复环境的名义扩大删除范围。
- 同环境、局部且无需持久化的检查直接给 Markdown 结果表。跨环境协调、数据生命周期或中断恢复按工作区规则使用 planning，用例条数本身不决定流程。
- HTML 只在用户要求可交付报告、跨环境正式验收或确需独立留档时生成，按 [报告规范](test-report-format.md) 校验；小报告无需额外计划。
- 逐例事实只保留一份：结果表或 HTML；有 plan 时 findings 保存事实或链接，progress 保存执行、统计与外部状态。计划总数与四类结果一致，未执行项说明原因，不能包装成通过。
